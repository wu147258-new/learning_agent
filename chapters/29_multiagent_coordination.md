# 多Agent工程协作：依赖图、共享状态与一致性

## 为什么增加Agent数量不一定提升速度

代码项目需要先完成缺陷定位，再生成补丁，最后运行测试。若三个Agent分别负责三个阶段，第二个必须等待第一个，第三个必须等待第二个；把三个角色同时启动并不能消除任务依赖。

真实协作还会增加额外问题：多份修改覆盖同一文件，测试基于旧版本，消息重复投递，多个Agent同时领取同一任务。多Agent首先是一个并发调度与状态一致性问题，其次才是提示词中的角色分工问题。

### 用任务依赖图描述流程

设任务集合为 $V$，依赖边集合为 $E$。若 $(v_i,v_j)\in E$，任务 $v_j$ 必须等待 $v_i$ 满足指定验收条件。

~~~text
读取仓库 ──→ 发现缺陷 ──→ 补丁生成 ──→ 回归测试
                 │               ↑
                 └──→ 风险评估 ──┘
~~~

如果A必须等待B，而B又必须等待A，则图包含环，调度器应拒绝并要求重新定义依赖，而不是无限等待。

### 为什么聊天记录不是任务状态

Agent之间的聊天可能丢失、截断或重复。调度器应该持久保存任务ID、输入版本、前置任务、授权工具、预算、运行状态、执行者租约与验收结果。聊天可以用于解释，不应该成为判断版本与权限的唯一依据。

## 从关键路径推导理论完成时间

### 最长依赖路径

设任务 $v$ 的耗时为 $t(v)\ge0$。对于依赖路径 $p$，总耗时：

$$T(p)=\sum_{v\in p}t(v).$$

路径上任务不能重叠执行，因此整个项目完成时间满足：

$$\boxed{T_{\rm finish}\ge T_{\rm cp}=\max_{p\in\mathcal P}T(p).}$$

这就是关键路径长度构成理论下界的原因，而不是一条纯粹的管理经验。

### 总工作量与工作者数量

设工作总量：

$$W=\sum_{v\in V}t(v).$$

如果有 $m$ 个能力相同的执行者，每单位时间最多处理 $m$ 个单位工作量，得到另一个下界：

$$T_{\rm finish}\ge W/m.$$

综合两个下界：

$$\boxed{T_{\rm finish}\ge\max(T_{\rm cp},W/m).}$$

这是假设任务可按既定耗时执行的理想边界；网络开销、模型推理成本、任务分配、故障恢复可能进一步增加耗时。

### 一道可计算的任务图

| 任务 | 耗时 | 前驱 |
|---|---:|---|
| A：读取代码 | 2 | 无 |
| B：定位缺陷 | 4 | A |
| C：依赖扫描 | 3 | A |
| D：生成补丁 | 5 | B、C |
| E：运行验证 | 2 | D |

总工作量为16。路径A→B→D→E的耗时13，路径A→C→D→E的耗时12，所以关键路径长度13。

即使有10名Agent，仍然不可能把这张图在少于13个单位时间内完成。真正优化重点可能是缩短B或D，而不是继续增加角色。

## DAG执行与可验证工件

### 定义任务输入和输出

一个子任务可以用以下字段记录：

~~~text
task_id
dependency_task_ids
input_artifact_ids
input_versions
required_permissions
cost_budget
output_artifact_id
output_version
acceptance_checker
~~~

后继任务只能依赖已经验收的输出版本，不能把“前一个Agent在聊天里说完成了”当作可靠状态。

### 拓扑排序只保证顺序合法

拓扑排序产生一组满足依赖约束的执行顺序，但不能保证所有行动执行成功，也不会自动保证每个生成的补丁正确。因此每一步都需要观察实际结果，遇到错误时更新状态、重新安排后续工作。

### 测试通过需要绑定代码版本

测试Agent报告“通过”必须附带被测试的代码提交或工作区快照。如果修改Agent之后再次变更同一函数，先前测试结果不能继续证明新版本正确。

合并两个各自通过测试的分支，也不能推出合并后的系统一定正确。不同分支可能改变了彼此依赖的接口，因此合并后应运行集成回归测试。

## 共享黑板与版本控制

### 为什么旧状态覆盖会发生

假设黑板状态版本为20：

~~~text
Agent-A读取版本20
Agent-B读取版本20
Agent-A提交测试约束 → 版本21
Agent-B以版本20覆盖写入 → 应拒绝
~~~

如果B没有版本检查就写入，可能把A新增的约束抹去。

### CAS原子比较与更新

让提交携带预期版本 $v$：

$$
\operatorname{CAS}(v,\Delta)=
\begin{cases}
\text{写入并把版本增加到 }v+1,&v=v_{\rm current};\\
\text{拒绝提交},&v\ne v_{\rm current}.
\end{cases}
$$

比较和写入必须属于同一个原子数据库操作；先读、在Python中检查、再无条件写入，仍可能存在竞争窗口。

### 并发写入冲突不是简单的文本冲突

两个Agent可以修改不同代码行，但更改组合起来仍可能使系统失败。例如A把函数改为异步，B沿用同步调用方式。即使Git自动合并成功，也必须重新执行系统测试。

## 消息重复投递与任务去重

### 为什么同一条消息可能出现两次

消费者处理完消息，但在确认之前崩溃，消息队列可能再次投递。若处理逻辑为“每收到一次任务就调用外部付费接口”，重复投递会产生重复费用。

可以用唯一事件ID及载荷指纹建立处理记录：

~~~sql
CREATE TABLE processed_events(
    event_id TEXT PRIMARY KEY,
    payload_hash TEXT NOT NULL,
    result TEXT NOT NULL
);
~~~

同一事件ID和载荷再次出现时，返回已有结果；若事件ID相同但载荷不同，应拒绝冲突。服务端数据库约束比“请不要重复处理”的提示词更可靠。

### 幂等与顺序是两类不同要求

即使每个事件都只执行一次，事件顺序也可能错误。例如先完成任务，再开始任务。系统应分别实施去重、版本比较、状态机转移与必要的任务顺序约束。

## 多Agent投票是否必然提高准确率

### 独立错误假设

设每个Agent独立判断正确的概率均为 $p$，采用三人多数票。若错误彼此独立：

$$P_{\rm majority}=p^3+3p^2(1-p).$$

若 $p=0.8$，则：

$$P_{\rm majority}=0.512+0.384=0.896.$$

这个结果有一个关键假设：三个Agent的错误独立。若它们使用同一模型、同一错误资料或同一推理套路，失败可能高度相关，不能把0.896当作真实实验结果。

### 多阶段任务更容易失败吗

若两个必需阶段分别以独立概率0.9成功，则任务整体成功概率为：

$$P(\text{均成功})=0.9^2=0.81.$$

这说明增加阶段和增加评审不是免费的。某个评审步骤若无法减少其他失败，就可能只增加新的出错点和延迟；是否值得必须由固定任务集上的实测决定。

## Handoff还是Manager调用专家：两种主流多Agent组织方式

### 专家接管与专家作为工具的区别

在实际Agent框架中，经常采用两种不同的协作关系：

- **Handoff**：协调Agent把当前任务的控制权转交给特定专业Agent，后者接管后续交互或执行；
- **Agents as tools**：Manager仍对用户任务负责，只把某个明确定义的子任务交给专家，专家返回结果后Manager再决定下一步。

OpenAI Agents SDK的官方编排文档明确区分这两种模式。它们不是仅把角色提示词换个名字，而是**任务控制权和最终结果责任**发生变化。

### Handoff的状态转移

假设客户提出计费投诉。协调Agent识别该任务需由账务专家处理。如果采用Handoff：

~~~text
用户 → 入口Agent → 账务Agent → 用户
                 控制权转移
~~~

Handoff前应明确传递用户意图、授权状态、必要历史和当前任务ID；不应无条件把所有敏感历史传给新Agent。Handoff不代表接管者获得高于用户原本权限的资源访问能力。

### Manager调用专家

对于代码审计报告，用户只与组长Agent交互，组长可调用检索专家和漏洞分类专家：

~~~text
用户 → Manager
         ├── 检索专家 → 返回带证据的结果
         ├── 代码分析专家 → 返回候选缺陷
         └── 验证器 → 返回独立测试结果
      → Manager汇总并向用户交付
~~~

Manager可以保持全局预算和结果整合责任；但若它只是把专家结果直接复制到最终报告，而没有检查来源、版本和权限，仍可能放大错误。

### 一次任务应该切换多少次Agent

过多Handoff可能增加上下文搬运、模型调用、工具重复执行和审计复杂度。假设每次转交额外开销为 $c_h$，总转交次数 $m$，则仅这部分开销：

$C_{\rm handoff}=mc_h.$

如果采用Manager调用专家，调用次数也会增加成本，并非完全免费。是否采用多Agent，应与单Agent加工具的基线比较成功率、延迟和费用，而不能单看协作角色数量。

### 模型、状态与权限的分离

一种适合大型工程开发的多Agent架构：

~~~text
任务/工单API
     ↓
协调服务与任务DAG —— 数据库中的任务状态、版本和预算
     ↓
独立Agent角色（规划/实现/测试/审计）
     ↓
受控工具网关 —— 角色权限、路径范围、幂等键
     ↓
代码仓库与测试环境
     ↓
外部验收器写入不可被Agent单独篡改的验收结果
~~~

这里的执行权不由提示词中的“总监Agent”或“高级专家”头衔决定，而由工具网关和可信身份记录决定。

### 从共享黑板到交付的具体规则

1. **任务状态**：任务DAG存在数据库，Agent聊天不作为权威状态。
2. **版本传递**：专家收到的输入工件必须带版本号或内容哈希。
3. **提交冲突**：输出写入黑板时采用CAS，遇到冲突重新读取并合并。
4. **权限检查**：工具每次执行重新检查身份、路径和预算。
5. **验收独立**：测试者不能直接修改不可变的验收规则或伪造测试通过。
6. **恢复**：发生超时后先查询是否已经执行，不盲目重试副作用。

这些规则对OpenAI Agents SDK、LangGraph以及自研执行器同样适用。

## 协调器与执行器分别负责什么

### 协调器维护全局依赖

协调器应保存DAG、可运行任务队列、输入工件版本、剩余预算、执行者租约、故障原因和验收状态。

### 执行器只执行明确授权的动作

执行器拿到任务后，应重新检查任务是否仍被授权、输入版本是否未变、预算是否可用，然后才执行工具。一个Agent即使拥有“组长”角色，也不能凭角色描述越过服务端工具权限。

### 并发上限和工作优先级

并行程度受关键路径、外部服务限流和资源争用限制。某个流程可以以最小化完成时间为目标：

$$\min T_{\rm finish}\quad\text{subject to }C_{\rm total}\le B.$$

若还有严重安全风险阈值，需要将它作为明确约束，而不是全部折算成一个无解释的“综合分”。

## 习题与选解

### 关键路径下界

**解：** 一条依赖路径中后继必须等前驱完成，路径上的任务耗时不能重叠；所以总完成时间不小于任意路径耗时，尤其不小于最长路径。

### 两个阶段成功率

**题目：** 两个独立且必须都成功的阶段，成功率各为0.9。总成功率？

**解：** $0.9\times0.9=0.81$，独立性不成立时不能直接相乘。

### 多数票概率

**题目：** 三个相互独立的分类器准确率均为0.8，三人多数票正确的概率？

**解：** 三人都对的概率0.512；恰好两人对的概率0.384；合计0.896。

### 编程与设计题

1. 修改任务图，让A依赖B且B依赖A，检查环检测器。
2. 两个执行者先读取版本20，再尝试写入，检查第二次更新是否拒绝。
3. 注入“处理成功但确认丢失”，检验重复消息不重复执行。
4. 比较1、2、4名工作者对固定DAG的理论下界。
5. 设计跨Agent集成验收，使结果只对应当前已合并版本。
