# 源代码安全审计Agent项目：污点分析、验证与可复核报告

## 为什么“扫描出一个危险函数”还不等于发现漏洞

某Python服务调用subprocess执行一个固定、预先登记的二进制程序。静态扫描器看到subprocess就报警，但该参数可能完全由系统配置生成、用户无法影响。另一个服务使用看似安全的路径拼接函数，却允许攻击者传入 ../ 访问受限目录。仅靠危险函数黑名单既会误报，也会漏报。

源代码审计需要回答：不可信输入从哪里进入？经过哪些变换和验证？最终到达了什么敏感操作？现有验证能否真正阻断攻击？系统运行权限与部署配置是什么？Agent应帮助分析这些问题，不能把模型置信度直接当作漏洞存在证明。

## 从入口、传播到危险汇点

### 数据流图

将程序表达为图 $G=(V,E)$，节点可以是变量定义、赋值、函数调用或数据变换，边表示值或依赖传播。污点源（Source）是用户输入、HTTP参数、上传文件名等，危险汇点（Sink）可能是SQL执行、命令执行、文件写入、敏感网络请求等。

### 污点传播

简单前向污点分析可将每个变量标记为tainted或untainted。若 $x$ 被污点标记，执行 $y=f(x)$ 且没有经过可证明的有效净化，则应谨慎地将 $y$ 也视为潜在污点。真实程序的别名、容器对象、反射、控制流和跨函数传播会使分析复杂化；教学版本需明确支持的语言子集和精度边界。

## 两个不同的安全例子

### SQL参数化

下面的写法将用户输入作为参数而不是拼接进SQL文本：

~~~python
cursor.execute(
    "SELECT id FROM users WHERE name = ?", (user_name,)
)
~~~

对于支持参数化的数据库驱动，这能避免把参数内容解析为SQL语法。参数化只保护参数值位置，不表示所有动态表名、排序字段或权限检查问题都已解决。表名等结构元素仍需固定映射或白名单。

### 不安全命令拼接

使用shell=True并直接拼接来自用户的字符串，存在命令注入风险。更安全的常见方案是调用明确路径的程序、将参数作为独立列表传入并关闭shell解释；但即使不用shell，被调用程序自身的参数语义、环境变量与文件权限也可能造成风险。

## 精度与可利用性边界

### 误报

假如某个参数来自不可修改的本地常量，静态工具因保守传播仍将其标记为tainted，可能产生误报。应保存完整路径和可信来源，允许人工复核。

### 漏报

动态字符串构造、反射、第三方库隐藏的数据流和未建模的函数可能让静态分析遗漏真实路径。审计报告要明确分析范围，不能声称“未发现漏洞”等于“没有漏洞”。

## Agent如何组织多阶段审计

### 资产和版本

先记录仓库commit、文件列表、语言、依赖版本与审计范围。没有固定代码快照，文件行号和补丁建议可能在审计过程中失效。

### 规则扫描

使用可复验的静态规则找到候选。每条候选记录文件路径、行号、规则ID和简短证据，而不是只有自然语言描述。

### 语义验证

沿着入口到汇点的数据流追踪，核对经过的净化和授权检查。需要时在隔离测试环境构造无害、可控制的测试输入来验证代码路径，但不得向生产系统进行未经授权的攻击。

### 风险评价

漏洞严重性依赖可利用前提、部署权限、数据敏感度、可达性和现有缓解机制。一个低权限不可达代码路径与公网可访问高权限入口的风险不同。需要区分技术危害与实际暴露程度。

## 可复现的审计报告结构

每条问题应包含：标题、风险类型、影响文件与行区间、源到汇点的数据流路径、攻击前提、当前验证状态、最小无害复现、修复建议、回归测试、引用的代码版本。未知的可利用条件应标为待验证，不应为了报告完整而编造。

### 已确认与怀疑的区别

一个模型认为“可能存在SQL注入”是待确认候选；若已证明不可信输入可控制SQL结构、且没有参数化保护，则可以给出更强判断。验证过程中若发现输入经过正确白名单限制，也应记录为误报并说明证据。

## 漏洞修复的端到端闭环

### 先写回归测试

修复前应使用安全测试数据重现预期失败，修复后确保输入被拒绝或作为普通数据处理。仅修改代码而不补充测试，后续容易出现回归。

### 最小补丁

优先修复根本原因，例如参数化SQL、路径规范化与目录约束、输入白名单和最小运行权限。不要通过简单删除日志、屏蔽告警或禁用检查来让扫描器不再提示。

### 独立复核

修复提交后重新运行静态规则、受控动态测试与相关业务回归，审查修复是否改变合法功能。对安全敏感变更应通过人工审查或明确的安全审批。

## 一个纯Python安全实验

examples/code_audit_dataflow_lab.py 构造最小赋值流图，手工标记输入节点，运行前向传播，区分安全与危险汇点；再设置模拟参数化边界并观察告警消除。程序不执行任何注入Payload，不访问网络或真实系统。

~~~bash
python3 examples/code_audit_dataflow_lab.py
~~~

## 习题与详解

### 题一：危险函数

代码中出现subprocess是否足以断言命令注入？

**解：** 不足以。要确认用户输入是否影响命令结构、是否通过shell解释、参数语义和运行权限等。

### 题二：参数化

为什么SQL参数化通常能阻断通过参数值改变SQL语法结构？

**解：** 数据库驱动将参数与SQL语法分离处理，输入值不再作为SQL语句的一部分解析；仍应验证使用方式正确。

### 题三：数据流

不可信输入x赋给y，y再传入没有验证的危险操作，审计系统该怎样处理？

**解：** 应沿赋值传播污点，标记对应源到汇点路径，随后分析是否有有效净化和运行前提。

### 题四：代码版本

审计发现对应文件v1，但系统已部署v2，为什么报告不能只写旧行号？

**解：** 行号与代码语义可能变化，应绑定commit、内容哈希与必要时的v2复核，避免引用错位。

### 题五：误报

某候选路径的输入来自固定常量，攻击者不可控制，应如何定性？

**解：** 在已确认来源不可控且无其他注入路径时，可以记录为该规则的误报或不可利用候选，并给出证据。

### 题六：测试环境

为什么不应在生产系统通过真实敏感数据验证漏洞？

**解：** 可能造成数据泄露或服务中断，应在授权隔离环境使用合成数据和无害方法复现。

### 题七：修复效果

扫描器不再报警是否足以证明漏洞已修复？

**解：** 不能。可能是规则被绕过或代码隐藏，仍应做数据流验证和业务回归。

## 延伸阅读

污点分析和静态程序分析有成熟形式化框架；真实应用安全审计应结合OWASP与相应语言/框架安全文档。Agent提供辅助定位与解释，不替代安全权限和独立审计结论。
