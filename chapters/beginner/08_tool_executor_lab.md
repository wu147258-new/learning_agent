# 综合实践：从零搭建一个受控工具执行器

## 任务描述：让程序处理结构化请求

设想某个助手收到下面的任务：

“计算7与11的和，并返回可以被另一程序读取的结果。”

如果只要求输出一段话，模型可能回答“答案是18”；但一个可集成的系统还需要明确输入格式、字段类型、工具权限、执行错误和结构化结果。

### 为什么从计算器开始

计算器本身没有模型推理能力，也不属于复杂Agent。但它拥有可精确验证的行为，特别适合作为工具执行器的第一步。确认可靠的执行基础以后，才有意义考虑引入语言模型、任务规划或概率决策。

本实验的输入：

~~~json
{
  "task_id": "demo-001",
  "tool": "add",
  "arguments": {"a": 7, "b": 11}
}
~~~

预期输出：

~~~json
{
  "task_id": "demo-001",
  "ok": true,
  "result": 18
}
~~~

如果请求包含不允许的工具名称、错误参数或未知字段，应产生明确的错误记录，而不是尝试执行“最接近”的操作。

## 输入如何变成数据

### 文本与对象是两个层次

接收到的JSON最初只是字符串。Python使用 json.loads 解析得到字典，但此时还不能认定字段正确。

~~~python
import json

text = '{"tool":"add","arguments":{"a":7,"b":11}}'
request = json.loads(text)

assert isinstance(request, dict)
assert request["tool"] == "add"
~~~

JSON语法合法只说明它符合序列化格式，并不说明请求的语义有效。程序还需要定义输入对象的结构、必填字段和类型。

### 为什么需要拒绝多余字段

某个工具只需要a和b，却额外收到执行路径、系统命令或管理员角色等字段。如果实现忽略这些字段，可能使调用者误以为它们有效；如果实现把未知字段直接转交给其他工具，则可能造成安全问题。

因此入门执行器采取严格方式：对每个工具规定允许的参数集合，发现多余字段就返回错误。生产系统可选择更复杂的兼容方案，但应在接口协议中明确说明。

## 工具注册与授权

### 从工具名查找执行函数

一个简化注册表可以写成：

~~~python
TOOLS = {
    "add": add,
    "multiply": multiply,
}
~~~

当请求中出现tool字段时，程序通过注册表找到对应函数，避免根据外部输入拼接任意Python代码并执行。

**绝对不要把模型生成的代码字符串直接传给 eval 或 exec，当作普通工具调用的默认实现。** 这两个函数可以执行任意Python表达式或语句，不属于通用安全解析器。

### 检查权限不能只检查函数是否存在

即使工具在注册表中，调用者也不一定具有权限。可以维护某个任务或用户允许执行的工具集合：

~~~python
allowed_tools = {"add"}
if request["tool"] not in allowed_tools:
    raise PermissionError("Tool not authorized")
~~~

真实系统的权限应由服务端身份信息与授权记录确定，而不是完全相信模型请求里附带的“我已授权”字段。

## 执行循环与状态记录

### 一次动作的最小状态

对只读计算器，可定义：

~~~text
RECEIVED → VALIDATED → EXECUTED → VERIFIED
                 ↓           ↓
                ERROR        ERROR
~~~

每次执行至少记录任务ID、工具名称、执行状态和可验证结果。若工具会修改文件或数据库，还需要记录操作所对应的版本及幂等标识。

### 失败是正常输出的一部分

假如输入为：

~~~json
{"task_id":"demo-002","tool":"add","arguments":{"a":"7","b":11}}
~~~

程序应报告整数类型不匹配，而不是让字符串"7"通过隐式猜测进入计算。

对于非法工具：

~~~json
{"task_id":"demo-003","tool":"delete_file","arguments":{}}
~~~

当前执行器应拒绝。不能因为语言模型声称操作“很安全”就绕过允许列表。

### 结果验证不应该只有模型自述

对于加法结果，可由独立的断言再次检查：

~~~python
result = 7 + 11
assert result == 18
~~~

对真实的代码修复，验证方式可能是运行测试和静态检查；对数据查询则可能是比较数据库约束与查询结果。验证器应尽可能独立于生成候选动作的模型。

## 一次完整运行

### 运行项目

仓库提供 **examples/beginner_tool_agent.py**。在项目根目录执行：

~~~text
python examples/beginner_tool_agent.py self-test
~~~

然后运行：

~~~text
python examples/beginner_tool_agent.py run
~~~

第二条命令使用内置样例请求并输出JSON结果，不需要API密钥、不需要Docker、不访问互联网。

### 检查输出和失败

程序的自检包括正常加法、乘法、非法字段、未知工具、布尔值冒充整数、没有授权以及模型输出中的恶意指令文本。

最后一种输入只作为普通字符串处理；执行器既不执行它，也不把它解释为新的权限指令。这样可以区分“外部数据包含文字”与“控制程序行为的授权命令”。

## 从受控工具到真正的Agent

### 还缺少什么能力

这个执行器只是**规则明确的工具执行系统**，并不能自主分解复杂任务。一个具备自主行动能力的Agent还需要：

1. 从环境获得可观察信息；
2. 根据任务和已有状态提出候选动作；
3. 决定哪些动作值得尝试；
4. 在工具反馈后更新状态与下一步选择；
5. 处理失败、预算、终止和结果验证。

这些功能可由固定工作流、搜索算法、概率模型或大语言模型分别承担。是否采用语言模型是一个工程选择，不是“能调用函数”的必要条件。

### 进一步抽象为条件分布

如果某模型根据当前状态 $S_t=s$ 产生多个行动候选，那么行动随机变量 $A_t$ 的条件分布可表示为：

$$P(A_t=a\mid S_t=s).$$

选定行动后，环境随机变化可通过：

$$P(S_{t+1}=s'\mid S_t=s,A_t=a)$$

描述。若每次动作都有成本随机变量 $C_t$，就可以进一步讨论累计成本期望：

$$\mathbb E\left[\sum_{t=0}^{T-1}C_t\right].$$

这里的数学对象分别对应模型选择、工具执行结果和实际消耗。后续章节会在此基础上研究任务规划与优化，而不是把执行器本身误认为一种训练算法。

## 练习与扩展

### 独立完成的任务

1. 增加subtract减法工具，要求拒绝布尔值、字符串和未知字段。
2. 为每次执行记录开始时间、耗时和结果，但不要将输入中的秘密信息原样写入公共日志。
3. 给同一工具注册两个版本，说明如何在结果中标注版本，便于复现。
4. 限制单次请求的整数绝对值不超过一百万，并编写边界测试。
5. 为返回结果加上verified字段，只有独立检查通过时才能为True。

### 开放题

当一个Agent需要修改真实文件时，仅靠这个计算器执行器还缺少哪些安全机制？从进程权限、路径约束、沙箱、版本回滚、并发和测试六个方面逐一列出。
