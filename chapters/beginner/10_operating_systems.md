# 操作系统基础：进程、线程与并发

## 为什么Agent需要理解操作系统

一个代码Agent执行测试时，测试程序陷入无限循环；另一个工具已经开始修改文件；用户此时按下取消按钮。需要回答：如何停止测试、回收子进程、保存已经完成的工作，并避免重复执行有副作用的操作？

这与进程调度、线程同步、文件系统和进程权限有关，不是靠语言模型生成一句“已取消”就能完成。

### 操作系统的基本任务

操作系统在应用程序与硬件之间提供抽象，管理处理器时间、虚拟内存、文件、进程及设备。程序不能直接假定自己独占机器；它请求操作系统分配资源，完成工作后释放资源。

### 程序、进程和线程

程序是存储在文件中的指令集合。进程是程序的一次执行实例，有自己的进程标识、地址空间、打开的文件和其他运行状态。

线程是进程内部的执行路径。同一进程的多个线程通常共享地址空间和文件等资源，但拥有各自的调用栈和调度状态。一个进程可以同时包含多个线程。

共享内存降低了通信成本，同时带来数据竞争风险。多个进程通常有更强的地址空间隔离，但如果它们拥有相同的文件权限，仍可能互相修改文件。因此“多开一个进程”并不等于实现了安全沙箱。

## 启动子进程和解释退出状态

### 用Python执行外部命令

~~~python
import subprocess
import sys

result = subprocess.run(
    [sys.executable, "-c", "print(2 + 3)"],
    capture_output=True,
    text=True,
    timeout=3,
    check=False,
)

print(result.stdout.strip())
print(result.returncode)
~~~

输出分别为5和0。第一个值来自子进程标准输出，第二个值是子进程退出码。

命令参数以列表形式提交，不借助shell拼接字符串，因此不会把任意特殊字符当作shell语法解释。但是若允许模型选择任意可执行程序及参数，仍可能执行危险命令。工具选择与授权必须由执行器检查。

### 退出码不等于任务验收

若测试程序退出码为0，却没有运行用户要求的测试用例，真实任务仍可能未完成。应区分：

$$
\text{进程执行成功}\ne\text{业务目标已经满足}.
$$

前者可由退出状态、错误日志判断；后者需要检查器验证指定文件、数据库状态、测试结果和副作用范围。

### 进程结束后的资源回收

父进程启动子进程后，需要在适当时候收集子进程的退出信息。某些类Unix系统中，子进程结束而父进程尚未回收退出状态时，会短暂保留进程表记录，称为僵尸进程。

这种进程已经停止执行用户代码，不能把它等同于仍在占用大量CPU的运行进程。通常需要父进程调用等待接口完成回收。Python的subprocess.run会等待所启动的程序完成，适合有限的同步命令。

## 并发与并行为什么不是同义词

### 并发表示多个任务在时间上交错推进

假设计算机只有一个处理器核心，同时运行三个程序。操作系统可以快速切换程序，让它们都得到执行机会。它们在同一时间段内取得进展，却不一定在同一瞬间执行。

这就是并发的一种情况。

### 并行要求同一时刻有多个执行单元

如果多个处理器核心真正同时运行不同任务，才有计算上的并行。并行任务通常也属于并发的工作负载，但不是所有并发都具有并行执行。

### 异步描述等待与继续执行的关系

异步程序可以在等待I/O操作时转去处理其他任务。例如等待网络响应期间，程序不必一直阻塞整个执行流程：

~~~python
import asyncio

async def simulated_request(name):
    await asyncio.sleep(0.01)
    return name + ":done"

async def main():
    values = await asyncio.gather(
        simulated_request("A"),
        simulated_request("B"),
    )
    assert values == ["A:done", "B:done"]

asyncio.run(main())
~~~

这是等待操作的并发，并不表示两项CPU密集计算自动在不同处理器上执行。若在协程中直接调用长时间阻塞的同步函数，仍然可能阻塞事件循环。

## 共享状态与竞争条件

### 丢失更新是怎样发生的

任务状态的版本号初始为10。执行者A和B都读取到版本10，接着分别准备更新：

~~~text
A读取版本10
B读取版本10
A提交新的结果，将版本改为11
B按旧版本10直接覆盖A的结果
~~~

如果写入逻辑没有检查版本，A的修改可能丢失。两个执行者的本地程序都没有语法错误，但组合执行的结果错误。

这种结果依赖操作先后顺序的错误称为竞争条件。

### 用互斥锁保护共享对象

~~~python
from threading import Lock

lock = Lock()
counter = {"value": 0}

def increment():
    with lock:
        counter["value"] += 1
~~~

如果所有相关线程都遵守同一把锁约定，就可以避免它们同时进入这个临界区。但线程锁不能直接保护另一进程或另一台服务器上的状态；跨执行器的共享数据通常需要数据库事务、条件更新或其他协调机制。

### 用版本条件避免陈旧写入

若数据库记录包含version字段，可以执行：

~~~sql
UPDATE tasks
SET status='done', version=version+1
WHERE task_id='t-001' AND version=10;
~~~

在数据库中检查影响行数。若为0，就可能是版本已变化，或任务已不存在。程序必须重新读取当前状态，而不是覆盖更新后的结果。

这称为乐观并发控制的一种形式：允许多个执行者先读取，但写入时核对原始假设是否仍然成立。

## 超时、重试和取消

### 超时是程序的一种正常结果

一个外部工具可能由于无限循环、网络丢包或依赖故障而迟迟不返回。执行器需要设置上限，而不能仅在提示词中要求“尽快结束”。

~~~python
import subprocess
import sys

try:
    subprocess.run(
        [sys.executable, "-c", "while True: pass"],
        timeout=0.2,
        check=False,
    )
except subprocess.TimeoutExpired:
    print("测试进程超过时间上限")
~~~

此例应只在受控的本地实验环境运行，避免将无限循环用作真实业务负载。对子进程树的完全清理、进程组信号、Windows作业对象等问题，还需要平台相关措施；单个timeout并不能解决所有进程管理问题。

### 结果未知与失败是不同状态

远程写入请求超时，可能是请求没有到达，也可能是服务端已经执行完操作，只是响应丢失。于是“没有收到成功响应”不等于“写入肯定没发生”。

对有副作用的操作，应优先查询外部执行状态，使用幂等键或可追溯请求编号，再决定是否重试。

### 取消后的状态怎样记录

一个可恢复任务常见状态为：

~~~text
PENDING → RUNNING → SUCCEEDED
                  ↘ FAILED
                  ↘ TIMED_OUT
                  ↘ CANCELLED
~~~

状态转移必须符合执行器实际观察到的事件。用户发出取消请求，只代表取消请求已经送达，并不自动证明外部工作已经停止。

对于长任务，检查点还需要保存已经执行的工具动作、外部请求标识、代码版本和结果哈希，避免重启后重复发起高风险操作。

## 文件系统、权限和内存

### 虚拟内存与持久状态

进程内的普通Python变量一般在程序退出后消失，不能用于长期保存任务进度。文件系统和数据库提供持久存储，但写入缓冲、事务提交和磁盘故障仍影响可靠性。

如果仅在语言模型的上下文中记住“已运行测试”，进程结束、上下文裁剪或代码版本变化后，记录可能不再有效。

### 路径和权限检查是两件事

文件路径用于定位对象，权限决定某个进程是否可以访问对象。例如一个工具只允许读取工作区目录，不能只做字符串前缀判断：

~~~text
/workspace/project-other/private.txt
/workspace/project/../secret.txt
~~~

这两个路径都可能通过天真的前缀检查。符号链接、路径规范化和并发替换也可能改变路径最终指向的对象。

真正的执行隔离需要结合文件系统权限、受限账户和操作系统支持的安全访问接口。

### 缓存结果为什么会失效

Agent保存了某次测试通过的记录。但如果代码随后修改，该记录只能说明**旧代码版本**通过测试。

缓存、测试结果、编译产物都必须关联源代码或输入数据版本。否则即使缓存命中率很高，也可能提高错误结果的使用频率。

## 队列与性能的基础数学

### 任务到达速度大于处理速度会怎样

假设服务每秒到达10个任务，但长期平均只能处理8个。若这种情况持续，未完成任务会越来越多，等待时间通常随之增长。

需要分别测量任务到达率、完成率、队列长度、单任务停留时间和资源占用，而不能只看CPU使用率。

### Little定律

在符合稳定性及长期平均条件的系统中：

$$\boxed{L=\lambda W}.$$

其中 $L$ 为系统内任务平均数量，$\lambda$ 为长期平均有效到达率，$W$ 为单个任务在系统内的平均停留时间。

例如平均每秒完成5个任务，平均停留2秒，则系统内平均有10个任务。

这个公式没有告诉我们应该配置多少线程或多少GPU。实际资源容量还取决于服务时间分布、并发限制、外部依赖和任务优先级。
