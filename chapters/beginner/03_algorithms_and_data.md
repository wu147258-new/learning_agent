# 算法与数据结构：让步骤变得可计算

## 从一万份日志中找到目标

假设需要从一万个日志文件中查找一个编号。可以从第一个文件开始逐个检查，也可以先建立索引，再快速定位。两种方法可能都能找到答案，但耗时会明显不同。

### 什么是算法

**算法**是一个由明确操作组成的有限求解过程。对于相同的输入，确定性算法在相同规则下得到相同的输出。定义算法时，需要区分：

- **输入**：问题实例是什么；
- **输出**：怎样判断答案正确；
- **步骤**：每一步允许做什么；
- **终止条件**：是否保证在有限步骤内结束；
- **资源成本**：需要多少时间和存储空间。

从计算机科学角度，算法不等于一段能运行的代码。代码是算法在某种语言和运行环境里的实现；算法的正确性与时间复杂度可以在实现之前讨论。

### 线性查找

~~~python
def find_index(items, target):
    for index, item in enumerate(items):
        if item == target:
            return index
    return -1

assert find_index(["a", "b", "c"], "b") == 1
assert find_index(["a", "b", "c"], "x") == -1
~~~

对于长度为 $n$ 的列表，最坏情况下需要检查 $n$ 个元素。把这种增长速度记作 $O(n)$。

$O(n)$ 并不表示“一定需要$n$秒”，而是在规模很大时，用于描述计算步骤数量随输入规模增长的上界量级。

## 二分查找为什么更快

### 先理解必须满足的前提

如果数据已经按大小排序，就可以先检查中间元素。若目标比中间元素小，右半部分不可能包含目标；反之左半部分可以排除。

~~~python
def binary_search(sorted_items, target):
    left, right = 0, len(sorted_items)
    while left < right:
        middle = (left + right) // 2
        if sorted_items[middle] < target:
            left = middle + 1
        else:
            right = middle
    if left < len(sorted_items) and sorted_items[left] == target:
        return left
    return -1

assert binary_search([1, 3, 5, 7], 5) == 2
assert binary_search([1, 3, 5, 7], 6) == -1
~~~

这个实现返回第一次出现的目标索引，因为右边界在遇到相等元素时仍然向左收缩。

**前提条件**是 sorted_items 已按比较规则升序排列。如果数据未排序，算法可能给出错误答案而不是抛出异常。

### 从重复折半推导对数复杂度

如果每次排除约一半候选，经过 $k$ 步后候选规模最多约为 $n/2^k$。当候选规模下降到1时：

$$\frac{n}{2^k}\le1
\quad\Longleftrightarrow\quad
2^k\ge n
\quad\Longrightarrow\quad
k\ge\log_2n.$$

因此二分查找的比较次数为 $O(\log n)$。当 $n=1024$ 时，对数级比较次数约为10次；线性查找最坏可能需要1024次。

但如果数据只用一次，而排序本身需要额外成本，先排序再二分查找未必比一次线性查找划算。**算法选择依赖整个工作量，而不是某一步的复杂度。**

## 列表、哈希表和树各适用于什么情况

### 列表适合保存顺序

Python列表支持按索引访问，平均情况下访问一个位置的成本与列表长度无关。向列表尾部追加通常是摊还 $O(1)$；在开头插入元素可能需要移动大量对象引用，成本为 $O(n)$。

如果任务必须按产生顺序处理，列表是直观的选择。若需要经常从前端取出元素，collections.deque 更适合。

### 字典为什么能快速查找

字典通常用哈希表实现。给定键，先计算哈希值，再通过表中对应位置寻找记录。平均情况下，键查找接近 $O(1)$，但碰撞和最坏情况不能忽略。

~~~python
status_by_id = {
    "task-001": "done",
    "task-002": "pending",
}
assert status_by_id["task-001"] == "done"
~~~

字典的键必须是可哈希对象。字符串和整数一般可以做键，列表不能直接做字典键。

如果目标是根据任务ID获取执行状态，字典通常优于每次遍历整个任务列表。

### 为什么还需要树

树是一种层次结构，由节点和边组成。文件夹、表达式语法树和任务分解都可能使用树结构。某些平衡搜索树支持按关键字有序查找、插入和删除，其典型复杂度为 $O(\log n)$。

但树不意味着“所有查询一定比字典快”；后者对精确键查询通常更直接，前者在顺序遍历、范围查询等场景有优势。

## 图：处理任务依赖的基础结构

### 图与树有什么区别

一个有向图记为 $G=(V,E)$：$V$ 是节点集合，$E$ 是从一个节点指向另一个节点的边集合。

假设完成部署需要先修改代码、再运行测试、最后发布，可以用有向边表示依赖：

~~~text
修改代码 → 运行单元测试 → 构建镜像 → 发布
                  ↓
             安全扫描
~~~

如果允许任务同时依赖多个前驱，就不一定是树。若不允许依赖环，结构称为有向无环图（DAG）。

### 广度优先搜索

在**无权图**中，从起点找到某个目标的最少边数路径，可以使用广度优先搜索（BFS）。

~~~python
from collections import deque

def shortest_hops(graph, start, goal):
    queue = deque([(start, [start])])
    seen = {start}
    while queue:
        node, path = queue.popleft()
        if node == goal:
            return path
        for nxt in graph.get(node, []):
            if nxt not in seen:
                seen.add(nxt)
                queue.append((nxt, path + [nxt]))
    return None
~~~

BFS先检查距离起点1条边的节点，再检查2条边的节点，如此逐层推进。第一次找到目标时，所用边数最少。

对于邻接表表示的图，若只记录父节点而不反复复制路径，BFS时间复杂度为 $O(|V|+|E|)$，空间复杂度为 $O(|V|)$。上面的教学实现为便于理解直接复制路径，可能额外消耗时间和内存。

### 当每条边的成本不同

某些操作耗时5秒，另一些耗时100秒。这时最少边数不一定意味着最小总时间。

Dijkstra算法在**边权非负**的条件下，可计算从起点到各节点的最小路径成本。它持续选择当前候选路径中总成本最小的节点，并检查是否可以改进相邻节点的成本。

负权边可能破坏算法的正确性。选择算法时，边权、是否存在环、能否准确估计成本都是必要条件。

## 递归、终止和正确性

### 递归为什么不能只看语法

递归函数在计算过程中调用自己。一个可靠递归算法需要：

1. 基础情形：能够直接得到答案；
2. 递归步骤：把问题转换为更小的同类问题；
3. 进展保证：经过有限次递归到达基础情形。

例如：

~~~python
def factorial(n):
    if type(n) is not int or n < 0:
        raise ValueError("n must be a nonnegative integer")
    if n == 0:
        return 1
    return n * factorial(n - 1)
~~~

可用数学归纳法证明对于非负整数 $n$，此函数返回 $n!$。但Python递归层数有限，对于非常大的$n$，应采用迭代方法避免递归深度问题。

### 证明与测试的作用不同

测试能够发现某些错误，但不能通过有限个具体样例证明所有输入下算法都正确。形式化证明通常依赖不变式、归纳法或其他数学工具。

对BFS而言，常用的不变式是：当节点按队列顺序处理时，已出队节点的最短边数距离已经确定。对二分查找而言，不变式是：如果目标存在，其首次出现位置始终处于当前候选区间。

在没有严格证明的工程项目中，仍应有针对边界条件的测试：空输入、重复数据、不存在的目标、孤立节点、循环依赖、大规模数据等。

## Agent的规划为什么离不开基础算法

自然语言任务经常包含明确的先后依赖。例如“先确认代码仓库权限，再读取项目，再修复错误，再执行测试”。对于可严格定义的部分，不必要求语言模型每一步重新发明工作流程；可以使用依赖图、状态机、搜索算法和外部检查器。

当需要在多个候选工具动作之间选择时，算法需要明确每个动作的前置条件、预计成本和可能副作用。模型可以提供候选方案，执行系统仍必须检查约束并记录状态。

一个简单的任务规划可分为：

~~~text
任务描述
  ↓
提取目标与前置条件
  ↓
构造任务依赖图
  ↓
检查是否存在环
  ↓
生成合法执行顺序
  ↓
执行、验证、失败时重新规划
~~~

如果依赖图含环，应报告冲突，而不应默默重复执行。若任务执行结果具有随机性，还需要在后续章节引入条件概率分布和数学期望。
