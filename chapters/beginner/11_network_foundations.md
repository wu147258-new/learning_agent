# 网络基础：从字节传输到可靠工具调用

## 为什么本地函数调用和网络调用不同

在一台计算机内调用函数，通常可以直接得到返回值或异常。调用远程服务时，中间增加了网络、远程进程、认证、协议解析和资源限制。

一次调用失败至少有几类可能：服务不可达、连接建立失败、请求发送不完整、服务端返回错误、服务端已经执行但响应丢失。它们不能全部写成同一种“模型调用失败”。

### 先区分网络、传输与应用协议

为了理解故障发生在哪里，可以分开看几个层次：

| 层次 | 核心问题 | 典型技术 |
|:--|:--|:--|
| 应用层 | 请求是什么、结果是什么 | HTTP、DNS、应用JSON协议 |
| 传输层 | 两个进程之间怎样交换数据 | TCP、UDP |
| 网络层 | 数据怎样到达目标主机 | IP |
| 链路层 | 相邻节点间如何传送帧 | 以太网、Wi-Fi |

这是一种解释结构，不意味着所有真实协议恰好按四层独立运行。例如TLS用于保护应用数据的传输，其具体位置可以跨越上述抽象边界。

### IP地址、端口和域名

IP地址用于网络层寻址，端口用于区分主机内的传输端点。一个TCP连接通常可由源地址、源端口、目的地址、目的端口等信息描述。

域名是便于人类使用的名字。DNS负责在其适用场景下把域名解析为网络地址等记录。**DNS解析成功不等于服务可用**：目标主机可能拒绝连接、端口没有监听、TLS校验失败，或者应用接口返回错误。

## 从字节理解TCP与UDP

### 网络传输为什么不是发送Python对象

Python字典、列表和自定义类对象是进程内的数据结构。网络传送的通常是字节序列，需要先把数据编码成双方都理解的格式。

~~~python
message = "你好，Agent"
wire = message.encode("utf-8")
assert isinstance(wire, bytes)
assert wire.decode("utf-8") == message
~~~

中文字符在UTF-8中可能对应多个字节。不能假定一个字符就等于一个字节，因此按字节长度限制工具输出时，需要考虑编码边界。

### TCP提供的可靠性究竟是什么

TCP面向连接，向应用提供有序的字节流，具有重传、流量控制和拥塞控制等机制。

但TCP**不保证一次send恰好对应对方的一次recv**。发送端把一个JSON对象分两次写入，并不意味着接收端会分两次读到同样的边界；反过来，多次写入也可能被一次读取合并。

因此需要应用层定义消息边界，例如消息长度前缀、换行分隔或HTTP中的报文结构。只依赖“read一次应该就收到完整JSON”会造成间歇性错误。

### UDP适用于哪些情况

UDP提供数据报通信机制，不建立像TCP那样的可靠字节流连接。应用收到的UDP报文可能丢失、乱序或重复，需要由应用决定是否进行确认、重试和排序。

某些协议会利用UDP减少连接与拥塞处理的成本，但这不意味着UDP总比TCP快，也不意味着使用UDP就一定不可靠。可靠性可以在其他层实现，代价与机制由具体协议决定。

## 连接建立和超时

### 连接超时与读取超时不同

客户端首先要找到目标地址并建立连接，然后发送请求、等待响应。连接阶段失败和服务器处理过慢属于不同问题。

对于HTTP客户端，常见的超时至少包括建立连接的上限与读取响应的上限；更完整的客户端还可能限制总请求时间。

### 什么时候可以重试

如果一次GET失败，重试可能合理；如果一次POST创建订单后响应丢失，立即重试可能创建两个订单。

安全重试需要考虑操作是否幂等、服务端是否支持唯一请求ID、失败发生的阶段、已重试次数以及总预算。简单的“捕获所有异常然后无限重试”会放大外部故障。

可将一次请求的执行状态表示为：

~~~text
CREATED → CONNECTING → SENT → RESPONSE_RECEIVED → VERIFIED
                        ↓             ↓
                     UNKNOWN        ERROR
~~~

当服务器是否完成操作未知时，不能把状态直接等同于FAILED；需要进一步查询或等待外部确认。

## HTTP请求怎样构成一个完整消息

### URL并不是程序执行命令

例如：

~~~text
https://api.example.org:443/v1/tasks?status=running
~~~

其中包含协议、目标主机、端口、路径以及查询参数。这些内容描述要访问的资源，不构成访问权限证明。

解析URL的程序只是在读字符串：

~~~python
from urllib.parse import urlsplit

parts = urlsplit(
    "https://api.example.org:443/v1/tasks?status=running"
)
assert parts.scheme == "https"
assert parts.hostname == "api.example.org"
~~~

真正发送请求之前，还需要确认目标是否属于允许的服务范围，避免把模型提供的任意URL直接交给具有内部网络权限的工具。

### 状态码、首部与响应体

HTTP响应可能包含状态码、首部和消息体：

~~~http
HTTP/1.1 200 OK
Content-Type: application/json

{"task_id":"t-001","status":"running"}
~~~

这里200表示HTTP处理成功，但消息体明确指出任务仍处于运行中。若把HTTP状态码等同于任务完成，就会产生错误的系统状态记录。

状态码404表示目标资源未找到，429常用于表示请求过多，5xx通常表示服务端处理异常。是否重试、延迟多久以及是否切换服务，要依据协议与应用约定，而不是仅凭一串数字猜测。

### JSON格式与请求体大小

结构化工具协议经常使用JSON。对接收端而言，需要先检查消息大小、编码和格式，再检查字段类型、取值范围和业务权限。

大模型产生的JSON即使语法合法，也可能包含错误工具名、参数越界、意外的嵌套结构或未知字段。因此传输可靠与语义正确是两个不同层次。

## TLS和身份认证

### 加密通道解决什么问题

在不可信网络上传输明文数据，可能遭遇被动窃听或中间人篡改。TLS通过加密、完整性保护及相关身份验证机制保护通信。

客户端访问HTTPS服务时，应正确校验服务器证书与主机名。为了“解决证书报错”而永久关闭证书校验，会削弱通信安全，尤其不适合处理API密钥与敏感数据。

### API密钥不应该写进源码

API密钥属于凭证，应该通过受控配置或密钥管理系统提供，避免直接提交到Git仓库、写入教材代码或出现在公共日志。

即使通过环境变量传入密钥，也要考虑同一主机上的进程权限、日志记录和部署平台的密钥暴露范围。环境变量是配置途径，不是独立的安全保险箱。

### 身份认证与授权不同

认证回答“请求是谁发起的”，授权回答“该身份允许执行什么操作”。一个已通过认证的用户不一定能读取任意客户记录，或者调用任意高风险工具。

Agent的工具权限应在服务端验证，不能以模型输出中的“已获得管理员许可”作为权限升级依据。

## 为什么Agent需要关注延迟、吞吐和成本

### 延迟是一次请求要花多久

假设一个Agent顺序调用三个服务，耗时分别为100毫秒、200毫秒和300毫秒，并忽略额外开销，那么总等待时间约为600毫秒。

如果三个调用没有数据依赖，能够安全并发执行，理想情况下总等待时间可能接近其中最慢的300毫秒；但线程调度、连接建立、服务端限流等因素会增加实际耗时。

只有操作互相独立时才能直接并行。若第二步需要第一步返回的任务ID，就不能为了缩短时间随意交换顺序。

### 吞吐率与高并发不是同一个量

吞吐率描述单位时间完成的工作量，并发数描述同一时刻正在处理的任务数量。服务可以有很高的并发连接数，却因为下游数据库变慢而得到很低的任务完成率。

实际Agent评测常需要同时报告：

- 完成任务的比例；
- 每个任务的总端到端耗时；
- 工具调用次数；
- 平均与尾部延迟；
- 超时、重试和失败占比；
- 按任务计算的资源费用。

尾部延迟例如第95百分位数表示约95%的观察值不大于相应阈值，在请求分布偏斜时比平均值更有诊断价值。

## 在本机搭建一个真实HTTP请求实验

### 为什么使用127.0.0.1

127.0.0.1是IPv4环回地址，通常指向本机。把服务绑定到这个地址，可以使实验在本机进行，不依赖公开互联网，也避免直接暴露给局域网其他主机。

不过环回网络服务仍然是可访问的本机资源，并非安全隔离边界；不要让本地测试服务处理真实业务凭证或危险操作。

### HTTP服务与客户端

标准库http.server可以构建一个只返回固定JSON的教学服务。客户端再使用http.client连接本机地址并读取响应。

运行：

~~~text
python examples/foundation_network.py
~~~

该实验自动分配临时端口、启动本机HTTP服务、请求两条路径并检查返回的状态码及JSON内容，完成后自动停止服务器。

### 应该测试哪些失败情况

除了正常请求，还可以尝试：

1. 请求不存在的路径，检查是否返回404；
2. 把读取到的JSON按错误编码解释，观察解码失败；
3. 构造不允许的HTTP方法，检查服务是否拒绝；
4. 令服务器返回任务状态running，验证客户端不会误写为completed；
5. 服务关闭后再次请求，区分连接失败与HTTP应用层错误。

每次实验都应记录实际请求、预期状态、收到的响应以及错误分类。
