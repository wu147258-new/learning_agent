# Agent运行时：持久状态、幂等执行与故障恢复

## 为什么正确计划仍可能执行失败

代码Agent收到任务：“定位配置错误，修改代码，测试并提交结果。” 规划器列出了正确步骤；第3步执行后进程突然退出。重启时必须回答：修改是否已经实际完成？是否可以安全重试？哪个版本的文件被修改？哪条外部证据足以证明步骤成功？

重新运行整个计划可能重复应用补丁、发送通知甚至扣费；简单跳过则可能遗漏本来就没有执行的动作。**运行时必须把“计划要做什么”和“已经验证做过什么”分开记录。**

### 将动作建议与执行许可隔离

规划器给出候选行动 $a_t$；执行器读取可信状态 $s_t$、用户身份 $u$ 后检查：

$$\operatorname{Allow}(u,a_t,s_t)\in\{0,1\}.$$

执行请求至少包含任务ID、步骤ID、操作类型、结构化参数、预期版本和幂等标识：

$$
r=(\text{task-id},\text{step-id},a,\text{args},v_{\rm expected},k).
$$

这些字段不是为了让模型写出漂亮日志，而是让并发、重试和审计拥有可核对的身份。模型生成“用户已授权”不构成真正的授权证明。

## 用状态机约束执行过程

### 准备、运行、成功与未知

单个步骤可采用以下有限状态：

~~~text
PENDING → PREPARED → RUNNING → SUCCEEDED
                     │
                     ├→ FAILED
                     └→ UNKNOWN
~~~

UNKNOWN不等于FAILED。调用邮件API超时后，服务端可能已经发送邮件但返回消息丢失。这种情况下，运行时不能直接认为发送失败，也不能无条件重试。

### 状态转移的数学定义

设状态集合为 $\mathcal S$，合法转移关系为：

$$\mathcal T\subseteq\mathcal S\times\mathcal S.$$

状态更新必须同时满足：

$$
(s_t,s_{t+1})\in\mathcal T,\qquad
v_{\rm stored}=v_{\rm expected}.
$$

第二个条件要求使用数据库原子条件更新。如果执行者A和B都读取版本7，A先提交版本8，B使用旧版本7继续写入就应被拒绝，而不是覆盖A的结果。

### 可以检验的不变量

运行时至少保持：

1. 一个任务步骤只有一条被接受的最终成功结果；
2. 未经授权的工具调用没有外部副作用；
3. 状态UNKNOWN不能被自动改写成SUCCEEDED；
4. 超出预算的动作不会被发送；
5. 过期租约持有者无法覆盖更新后的资源。

所有这些性质都可以被编写成确定性单元测试，而不能只写进提示词。

## 为什么先执行或先记录都会留下故障窗口

### 先执行再记录

~~~text
外部请求已执行成功
    ↓
执行器崩溃，没来得及写本地日志
    ↓
重启后找不到成功记录
    ↓
又发了一次相同请求
~~~

这可能导致重复副作用。

### 先记录成功再执行

~~~text
本地数据库写入SUCCEEDED
    ↓
执行器崩溃
    ↓
远程操作根本没有发生
~~~

本地日志成为虚假完成证明。正确做法是将**意图记录**与**执行确认**分开。

### 准备日志与结果日志

一种简单协议：

1. 持久记录PREPARED状态，并生成唯一操作ID；
2. 向远端接口发送带操作ID的请求；
3. 收到响应后，或通过操作ID查询外部执行状态；
4. 只有验证得到明确结果才写入SUCCEEDED；
5. 若没有可靠证据，进入UNKNOWN，等待查询或人工处理。

能否安全重试，取决于服务端协议。如果远端不支持幂等键，不能声称这套流程保证了业务效果“恰好一次”。

## 数据库事务能保证什么

### 建立任务步骤表

~~~sql
CREATE TABLE steps (
  task_id TEXT NOT NULL,
  step_id TEXT NOT NULL,
  status TEXT NOT NULL,
  version INTEGER NOT NULL,
  operation_key TEXT NOT NULL,
  PRIMARY KEY (task_id,step_id),
  UNIQUE (operation_key)
);
~~~

主键防止本地同一个任务步骤重复插入，唯一约束防止同一操作标识重复绑定不同步骤。但这些约束只能控制本地数据库，无法自动约束远程服务。

### 原子条件更新

~~~sql
UPDATE steps
SET status = 'RUNNING', version = version + 1
WHERE task_id = ? AND step_id = ?
AND status = 'PREPARED' AND version = ?;
~~~

执行后检查受影响行数。若为0，状态或版本已变化，不能认定更新成功。原子比较与写入必须由数据库完成，不能由模型先读旧版本、再在一段自然语言里说“我检查过”。

### 为什么外部API不自动加入数据库事务

SQLite事务能够保护同一数据库内按事务协议执行的写入，但发送邮件、修改远程仓库或调用第三方接口不因此成为SQLite事务的组成部分。跨服务的一致性通常需要去重协议、可靠事件通知、补偿操作、可查询的外部状态等额外机制。

## MCP工具契约：从模型提议到受控执行

### 为什么需要结构化工具协议

前面已说明，模型生成的动作不等于系统授权。本节进一步讨论一个实际工程接口：模型提出读取告警的请求，执行器怎样在调用前核对参数、租户、权限和调用结果？

MCP（Model Context Protocol）2025-11-25规范将参与者分为Host、Client与Server，基于JSON-RPC 2.0通信。Server可以提供Tools、Resources、Prompts；工具负责执行操作，资源用于提供上下文，二者不应混淆。

### 工具调用的消息结构

MCP提供tools/list用于发现工具、tools/call用于调用工具。一个简化的JSON-RPC请求示例如下：

~~~json
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "read_alert",
    "arguments": {"alert_id": "A-102"}
  }
}
~~~

真实服务还需完成初始化、能力协商和适用的认证过程，不能把这一消息当成完整的网络会话。

### Schema验证不等于授权

假设read_alert要求告警编号满足前缀A-及若干数字。即使输入格式正确，也不能证明调用者有权查看该告警。服务端必须使用可信身份对应的租户信息过滤数据：

~~~sql
SELECT alert_id, summary
FROM alerts
WHERE tenant_id = ? AND alert_id = ?;
~~~

可以将许可条件写成：

$
\operatorname{Permit}(u,r,a)
=
\operatorname{Authenticated}(u)
\land\operatorname{AllowedScope}(u,a)
\land\operatorname{ResourceAllowed}(u,r).
$

模型不能仅凭参数中填写另一个租户标识，改变真实授权范围。

### 工具元数据与权限的信任边界

工具描述可能由外部Server提供，是需要校验的数据，而不是能修改服务端权限策略的授权指令。特别应避免把远端描述的自然语言直接映射成高权限系统操作。

MCP官方安全实践还特别说明Token Passthrough与Confused Deputy风险：服务端应验证访问令牌受众、范围和有效期，不能不经验证地将客户端令牌直接当作下游服务凭证。

### 重试时区分两种ID

JSON-RPC消息中的id主要负责关联请求和响应，业务写入动作的幂等效果则需要单独的操作标识、服务端去重和执行结果查询机制。不能把同一个id当作外部业务已被恰好一次执行的证明。

### 教学实验与思考

运行：

~~~bash
python examples/agent_protocol_contracts.py
~~~

实验验证方法名、参数模式、授权租户和稳定业务操作键，并拒绝重复键与不同请求内容的组合。它模拟协议边界，不是完整MCP SDK实现。

**习题：** 如果用户只具有读取权限，但MCP服务端公开了一个写入工具，是否能调用？为什么？

**解：** 不能。服务端存在某工具与当前用户具有工具执行权限是不同命题；写入操作需要独立的真实授权。

## 业务效果恰好一次的限制

### 至多一次与至少一次

至多一次尝试可以降低重复副作用，但可能丢失任务；至少一次尝试可以提高最终执行机会，却要求远端能安全处理重复。

对于跨服务操作，业务效果恰好一次往往依赖远端原子去重记录，而不是网络本身“恰好投递一次”。**不要把本地步骤执行一次等同于外部业务效果恰好一次。**

### 服务端幂等键

设请求为 $(k,p)$，其中 $k$ 是唯一操作键、$p$ 是请求内容。远端保存第一次处理结果 $R(k)$，再次收到相同键及相同内容时返回原结果，而不重复执行副作用。

如果重复使用相同键但请求内容不同，服务器应拒绝或明确处理冲突；否则错误的键复用可能掩盖不一致的业务动作。

## 租约、心跳与栅栏令牌

### 租约失效后的旧执行者

执行者A获得任务租约并开始执行，随后暂停。租约到期，执行者B接管。A突然恢复，两个执行者同时拥有本地运行能力。

仅靠超时删除锁无法解决问题：A可能还在执行旧任务。

### 栅栏令牌

为每次新的持有者提供严格递增令牌：

$$f_1<f_2<f_3<\cdots.$$

A持令牌5，B持令牌6，实际接收写入的资源必须拒绝令牌5的陈旧操作。令牌必须由可信存储或协调服务维护，并由下游检查；只把令牌附在模型回复里没有任何隔离作用。

### 心跳的边界

心跳只能反映某时间点执行者仍在报告状态，不代表前一次业务动作成功。进程存活、执行完成与业务验收是三种不同的证据。

## 重试、超时与成本上限

### 指数退避

如果请求可安全重试，可以设第 $n$ 次等待：

$$
d_n=\min(d_{\max},d_0\,2^n).
$$

实际服务可加入随机抖动，避免大量执行者同时重试。**退避不等于幂等**；未知结果的写操作即使等待很长时间也不能盲目重发。

### 预算不是提示词约定

设已经确认发生的成本为 $\sum_{i<t}c_i$，下一个动作预计保留成本为 $\widehat c_t$，则必须在发送请求前检验：

$$
\sum_{i<t}c_i+\widehat c_t\le B.
$$

真实计费结果可能比估算高或低，因此还需约定预留成本、结算、失败退款和并发预算占用方式。执行器必须在持久状态里执行预算约束。

## 检查点、事件日志与版本

### 为什么要同时保存快照和事件

快照保存某个时刻的完整任务状态，事件日志记录其后的状态变化：

~~~text
snapshot(version=100,status=RUNNING)
event 101: request_prepared
event 102: external_result_observed
event 103: evidence_verified
event 104: step_succeeded
~~~

若只有准备事件而没有外部结果，恢复程序必须先调查该操作是否发生，不能凭缺少日志推断未执行。

### 重放也需要版本信息

事件模式、执行器代码、工具协议和校验规则可能随时间变化。重放记录应关联这些版本。用新代码毫无转换地解释旧事件，可能产生语义不兼容。

对含密钥或个人数据的日志，必须设定访问边界、脱敏规则和保存期限；审计需要真实证据，不意味着可以永久保留所有原始输入。

## 对照LangGraph与Agents SDK：运行时框架怎样实现状态与审批

### LangGraph检查点具体保存什么

前面已经讨论了状态快照、事件记录和任务版本。LangGraph公开文档中的图执行、检查点与中断恢复，是这些概念在实际Agent框架中的一种实现路径。

当图节点需要人工批准时，可以通过interrupt机制暂停，并通过持久化层保存图状态；外部审批结果到达后再通过指定线程标识恢复。

这里有一个容易忽略的重要细节：**恢复可能从被中断节点的起点重新执行该节点**。因此，节点里如果在调用中断之前执行了有副作用的操作，恢复时可能再次执行这个副作用。真正的设计需要把高风险动作放在审批完成之后，并为远端操作增加幂等键。

### 从框架机制推导的安全节点拆分

一种比“一个节点里什么都做”更明确的设计：

~~~text
Node A：生成候选补丁（只读或临时沙箱）
    ↓
Node B：保存计划 + 发出审批请求（可恢复）
    ↓
用户或授权服务返回批准/拒绝
    ↓
Node C：再次验证授权与代码版本
    ↓
Node D：携带幂等键实际写入
    ↓
Node E：独立测试和版本确认
~~~

如果把写入操作放在Node B暂停之前，恢复时存在重复执行风险。把操作拆开能够让权限与执行边界更清楚，但并不自动获得跨系统的恰好一次语义。

### OpenAI Agents SDK的Agent循环与恢复责任

公开的Agents SDK把Agent循环、工具调用、Handoff、Guardrail和人工审查整合为代码级构件。一次运行通常调用模型、解析工具或Handoff指令、执行工具、继续循环，直到获得完成结果或明确的暂停点。

关键的工程问题仍由业务系统回答：哪个任务版本获授权、有哪些外部副作用、哪个检查点已经持久化、需要保存多长时间、如何删除敏感日志。**运行时框架提供机制，不代替业务安全策略与数据库一致性设计。**

### 两种框架的关注点比较

| 方面 | 图状态机/检查点思路 | Agent循环/工具Handoff思路 |
|---|---|---|
| 核心抽象 | 节点、边、共享图状态 | Agent、工具、Runner与Handoff |
| 中断与恢复 | 指定检查点恢复图执行 | 用运行状态、审批机制暂停和继续 |
| 适用任务 | 审批多、分支复杂、长期持久任务 | 模型工具循环、专业Agent切换 |
| 业务幂等 | 仍需外部操作ID和结果查询 | 仍需外部操作ID和结果查询 |
| 版本一致性 | 需要正确管理图状态与工件版本 | 需要正确管理会话和工件版本 |

不要因为某框架有checkpoint，就在简历或报告中声称已经实现“所有外部操作恰好一次”。真正的验收实验应在调用成功但响应丢失、节点重复执行、审批前后状态变化三类情况下验证结果。

## 运行实验：崩溃后恢复

### 离线实验结构

执行：

~~~bash
python examples/agent_runtime_recovery.py
~~~

实验创建SQLite任务表与模拟远端服务，执行：

1. 从PENDING写入PREPARED并生成幂等键；
2. 远端实际完成副作用，但模拟丢失响应；
3. 本地进入UNKNOWN；
4. 恢复时使用同一幂等键查询或重试；
5. 远端返回首次处理结果，副作用计数仍为1；
6. 版本条件更新拒绝陈旧执行者；
7. 未授权和超预算请求不产生副作用。

测试仅验证本实验的远端去重协议；真实API未必具有相同语义。

## 习题与解答

### 先执行再记录为何不能保证恰好一次

**解：** 外部成功和本地日志之间存在崩溃窗口。本地没有确认记录并不证明外部没有执行。只有可靠的服务端去重或其他跨系统协议才能提供相应的业务保证。

### 两个执行者同时读取版本7

**解：** A将版本更新为8后，B使用旧版本7的条件UPDATE应影响0行。B必须重新读取当前状态，不能把0行写入报告为成功。

### 过期租约会发生什么

**解：** 过期执行者A即使恢复运行也不应覆盖B的操作。下游需要拒绝A持有的旧栅栏令牌；单靠A自己检查租约不足以保证安全。

### 进一步练习

1. 为RUNNING、UNKNOWN和SUCCEEDED定义合法转换表，并编写拒绝非法转换的测试。
2. 去掉远端幂等键去重，重放同一故障，观察副作用计数的变化。
3. 把内存SQLite改为文件数据库，演示进程重启后的状态恢复。
4. 设计租约过期而旧执行者恢复的时序，验证下游栅栏令牌比较。
5. 将预算改为共享并发预算，思考为什么单纯“先读余额再扣减”会发生竞争。
