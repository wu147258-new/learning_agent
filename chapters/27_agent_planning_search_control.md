# Agent规划：状态空间搜索、随机控制与可验证执行

## 从一个需要多个步骤的实际任务开始

用户提出：“检查代码仓库中的身份认证缺陷，确认问题后修改代码，运行测试并提交报告。”

这个目标不能直接视为一次文本生成。完整任务需要至少完成：确定检查范围、读取必要文件、识别缺陷、产生修复方案、取得写入授权、应用修改、运行验证和形成报告。每一步可能失败，而且一些操作具有不可逆的外部副作用。

规划问题的核心是：**给定当前状态、目标条件、可用行动及约束，计算一组预期能够达到目标的行动，并在执行后根据实际结果重新判断。**

### 什么是状态

为了使问题可计算，定义状态集合 $\mathcal S$。例如：

$$s=(\text{仓库版本},\text{已读取文件},\text{测试状态},\text{剩余预算}).$$

状态是对系统执行所需信息的数学抽象，不等于模型自述“我目前理解了什么”。状态中没有保存的信息，可能导致规划器做出与真实环境不一致的判断。

### 什么是行动

行动集合 $\mathcal A(s)$ 表示当前状态允许执行的操作，例如只读检索、运行受控测试、提交待审核补丁。每个行动都有前置条件、成本和可能产生的状态变化。

如果当前用户没有写入权限，写入操作即使能够被语言模型提出，也不应被执行器视为合法行动。**合法性由外部授权记录决定，不由模型生成的声明决定。**

### 什么是目标

目标是状态上的可检查条件：

$$G(s)\in\{0,1\}.$$

例如：

- 指定的测试集合已经运行且通过；
- 修改只影响获授权的文件；
- 原缺陷被独立检查器确认消除；
- 报告包含真实代码版本和可核查证据。

如果仅把“模型回复了任务已完成”作为目标，就可能在没有执行实际检查的情况下错误地终止任务。

## 确定性规划：先从最短路径开始

### 把任务表示成图

设状态为图的顶点、行动为有向边。行动 $a:s\to s'$ 具有非负成本 $c(s,a)$。

例如：

~~~text
开始 --成本1--> 初查 --成本10--> 完成
  |               |
 成本3           成本1
  |               |
  v               v
 审核 --成本2--> 完成
~~~

另有从初查到审核的成本1边。图中最少边数的路径不一定具有最低总成本。

### BFS适用于什么情况

广度优先搜索（BFS）按照边数逐层搜索。在所有边成本相同的无权图中，第一次到达目标可得到最少边数路径。

但若上例成本不同，BFS可能找到“开始→初查→完成”，只有两步却需要成本11。另一条“开始→初查→审核→完成”有三步、总成本4。

BFS保证的是**最少边数**，不是任意加权图中的最小成本。

### Dijkstra为什么能处理不同成本

在边成本非负时，Dijkstra算法始终扩展当前已知累计成本最小的状态，并通过松弛更新相邻状态：

$$
g(s')\leftarrow
\min\{g(s'),\,g(s)+c(s,a)\}.
$$

当目标首次以当前最小成本出队时，能够得到最小累计成本。若存在负权边，普通Dijkstra的保证不再成立。

实际Agent任务中，边成本可以是执行时间、API费用、人工审核成本或复合指标。但把多个不同单位直接相加，必须先说明权重与量纲，不能只用一个随意的“综合成本”掩盖风险。

## A*搜索：把已发生的成本与剩余估计结合

### 评价函数从哪里来

Dijkstra不利用与目标有关的额外信息。A*为每个状态构造：

$$
f(s)=g(s)+h(s),
$$

其中：

- $g(s)$：从起点到当前状态已经发生的路径成本；
- $h(s)$：从当前状态到目标的剩余成本估计。

A*优先扩展 $f(s)$ 较小的状态。

### 可采纳启发式

若真实最优剩余成本为 $h^*(s)$，启发式满足：

$$
0\le h(s)\le h^*(s),
$$

则称其为可采纳（admissible）。它不会高估剩余成本。

对于前面的图，取：

$$h(\text{目标})=0,\quad
h(\text{审核})=2,\quad
h(\text{初查})=3,\quad
h(\text{开始})=4.$$

这些数字恰好是该图上的真实剩余最优成本，因此属于可采纳启发式。

### 一致性使搜索更容易正确实现

更强的条件是：对于每条边 $s\to s'$，

$$
h(s)\le c(s,a)+h(s').
$$

这称为一致性（consistent）。非负成本加上一致启发式，使常见的图搜索实现能够在状态从优先队列正式取出后安全地标记为已完成。

若启发式只有可采纳性、未满足一致性，实现可能需要重新打开此前扩展过的状态，不能简单照搬不重开节点的版本。

### 为什么“模型觉得距离目标很近”不能直接用于最优性证明

大模型可以估计一个任务还需要多少步，但这种估计未必是可采纳的，它可能大幅高估实际剩余成本。

因此如果使用模型启发式，就不能未经测试宣称A*依然保证最优。可以采用保守下界、独立计算的松弛问题或仅将模型估计用于排序而不做最优性保证。

## 任务依赖图与规划顺序

### 不是所有任务都能任意交换

假设必须先读取文件，再形成补丁，然后运行测试。依赖关系可以写为：

$$
\text{读取}\prec\text{修复}\prec\text{验证}.
$$

若存在两个互不依赖的测试，它们可以并发执行；如果两个操作同时写同一个文件，则必须明确版本冲突和写入顺序。

对有向无环图（DAG），可用拓扑排序给出一个满足全部先后约束的执行顺序。若依赖图包含环，例如“A依赖B、B依赖A”，就需要重新定义任务，而不是让执行器无限等待。

### 规划顺序与执行顺序仍有差别

即使拓扑顺序合法，也不代表每个操作都执行成功。实际工具执行可能改变环境、产生新依赖或提前使目标成立。

可靠的执行器每步都会记录：

$$\text{计划动作}\longrightarrow\text{执行结果}\longrightarrow\text{新观测状态}.$$

若实际状态与预期状态不同，就要重新搜索或进入明确的失败处理，而不能沿着过期计划继续执行。

### 计划生成阶段

输入包括目标、当前状态、合法动作、预计成本、权限和资源上限。输出是候选行动序列及其预期前置条件。

规划器可以是确定性搜索算法，也可以调用语言模型生成候选动作。但无论来源如何，候选动作进入执行器前都要通过结构化校验和授权检查。

### 执行阶段

每次执行之前确认当前状态版本仍与计划一致。若其他执行者已经修改状态，应重新获取状态，而不能在陈旧快照上覆盖写入。

对有副作用的工具，还应记录唯一请求ID和外部确认信息。网络超时后，不应简单认为“没有收到成功响应，所以动作没发生”。

### 验证与恢复

成功必须由独立检查器验证。对于代码修复，可以运行原缺陷复现测试、回归测试以及文件差异检查；对于检索问答，可检查证据版本与引用是否成立。

失败后先区分：

1. **可确认未执行**：可以考虑重新规划或按约定重试。
2. **可确认已执行但目标未达成**：需要更新状态、可能执行补救操作。
3. **外部结果未知**：必须先查询外部状态，不应盲目重复写操作。

这三类状态不能全部当作“失败，重试一下”。

## 把A*转换为可运行的搜索程序

### 状态和行动必须是结构化对象

一个简单的规划图可定义为：字典的键是状态，值是可执行行动的列表。每个行动有后继状态、成本与所需权限。例如：

~~~python
graph = {
    "start": [
        ("risk", 1, "read"),
        ("audit", 3, "read"),
    ],
    "risk": [
        ("goal", 10, "deploy"),
        ("audit", 1, "read"),
    ],
    "audit": [
        ("goal", 2, "deploy"),
    ],
    "goal": [],
}
~~~

如果没有deploy权限，则通往goal的边不属于合法行动。规划器不能把“我认为部署很重要”当作绕过权限的理由。

### 最小A*循环

~~~python
from heapq import heappop, heappush

def astar(start, goal, edges, h, permissions):
    frontier = [(h[start], 0, start, [])]
    best = {start: 0}
    while frontier:
        _, cost, state, path = heappop(frontier)
        if cost > best[state]:
            continue
        if state == goal:
            return path, cost
        for nxt, edge_cost, scope in edges[state]:
            if scope not in permissions:
                continue
            if edge_cost < 0:
                raise ValueError("negative edge cost")
            candidate = cost + edge_cost
            if candidate < best.get(nxt, float("inf")):
                best[nxt] = candidate
                heappush(frontier, (
                    candidate + h[nxt], candidate,
                    nxt, path + [nxt]
                ))
    return None
~~~

这段教学代码假设状态可以比较、成本非负，且给定的启发式满足所声称的条件。完整实验另外实现了稳定的优先队列顺序、边校验、失败后阻止重试的动作记录和执行阶段再次检查权限。

### 为什么执行阶段仍须再次检查权限

规划器读到的权限可能已经在执行前被撤销。仅在规划时检查一次，不足以保证真正执行工具时仍有权操作。实际执行器应从可信授权源重新核验动作、资源范围和请求版本，检查通过后才实施具有副作用的操作。


## 行动具有随机结果时怎样计算规划价值

### 确定性图不够用

假设某个检查动作有80%概率立即发现并解决问题，20%概率进入需要额外处理的状态。

在这种情况下，同一个状态执行相同行动，下一状态并不唯一。可用条件分布表示：

$$P(S_{t+1}=s'\mid S_t=s,A_t=a).$$

每个行动可能还有即时随机成本 $C_t$。规划目标之一是寻找使累计成本数学期望最小的行动条件分布或确定性选择规则。

### 用全期望公式建立Bellman递推

对于有限时域、终端成本为0的情形，设 $V_t(s)$ 为时刻 $t$ 处于状态 $s$ 时，后续最小期望成本。

在合法行动集合 $\mathcal A(s)$ 上：

$$
\boxed{
V_t(s)=\min_{a\in\mathcal A(s)}
\left[
c_t(s,a)+
\sum_{s'}P(s'\mid s,a)V_{t+1}(s')
\right].
}
$$

这来自条件期望的线性性、全概率公式和在当前状态下选取最小条件期望成本。这里的 $c_t(s,a)$ 表示已将即时随机成本取条件期望的结果。

如果行动还有安全风险、时间上限或授权约束，不能只优化一个无约束平均成本；应把相关限制明确写入合法行动集合、风险约束或多目标评价中。

### 一道两行动手算题

当前可以选择：

- 稳妥执行：成本5，必定到达终点；
- 尝试快速路径：即时成本1，80%直接成功；20%进入故障恢复状态，后续成本10。

快速路径的期望总成本：

$$1+0.8\times0+0.2\times10=3.$$

只以期望成本为目标时，应选择快速路径（3小于5）。但若不允许出现额外10的故障恢复风险，或必须遵守严格的完成时间要求，选择可能不同。这说明最小期望成本与风险控制是两个问题。

## 状态无法完全观察时怎么办

### 观测不等于真实状态

假设服务器是否已修复是隐藏状态 $S$，只观察到一次健康检查结果 $O$。一次成功的网络响应并不一定意味着全部故障都已经消除。

可以维护关于隐藏状态的条件分布，也称为信念状态：

$$b_t(s)=P(S_t=s\mid O_{0:t},A_{0:t-1}).$$

它是一个概率分布，不是大模型随意填写的“置信度”。

### 从先验推导后验

假设服务器故障先验概率0.1，健康检查告警在真实故障时的概率为0.8，在正常时误报概率为0.05。

观察到告警后的故障概率：

$$
P(F\mid+)=
\frac{0.8\times0.1}
{0.8\times0.1+0.05\times0.9}
=\frac{0.08}{0.125}=0.64.
$$

这表示获得告警证据后，按给定模型故障概率更新为64%，不意味着故障已被确定。是否执行修复，还要结合修复成本、误修风险及进一步检查的价值。

### 贝叶斯状态更新

若行动 $a$ 后产生观测 $o$，先对隐藏状态进行转移预测：

$$\widetilde b_{t+1}(s')
=\sum_sP(s'\mid s,a)b_t(s).$$

再用观测似然更新：

$$
b_{t+1}(s')=
\frac{P(o\mid s',a)\widetilde b_{t+1}(s')}
{\sum_uP(o\mid u,a)\widetilde b_{t+1}(u)}.
$$

这就是部分可观察序列决策中常见的信念状态更新。实际系统中需要估计转移与观测模型，否则得到的概率只是建立在假设上的数值。

## Agent规划的三种实现路径

### 固定工作流

对于步骤明确、不能自由改变顺序的任务，可以采用固定DAG或状态机。优点是容易审计、约束清晰；局限是对未知故障缺少灵活性。

### 基于搜索的规划器

如果行动、状态转移与成本可以列举，就能使用BFS、Dijkstra、A*、动态规划或其他搜索方法。每次扩展动作时，由确定性规则判断前置条件与授权。

这种方式适合有限任务空间、代码构建流水线、明确的运维操作图。空间太大时，需要状态抽象、启发式或候选生成，不能直接枚举所有状态。

### 大模型提出候选动作

当自然语言任务难以直接转成固定图，模型可以负责把目标转成子任务并提出工具候选。但它提出的动作仍需经过类型校验、权限校验、预算检查以及独立验证。

“模型想到了操作”与“系统允许执行操作”是完全不同的事件。模型建议器和工具执行器应分开设计，尤其不能让模型直接修改自己的授权列表或检查器。

## 把搜索算法落到ReAct和Plan-and-Execute两种Agent架构

### ReAct为什么在行动之间插入观察

前面把规划定义成状态 $s_t$、合法动作 $a_t$、环境反馈 $o_{t+1}$ 的交替过程。ReAct（Reasoning and Acting）是这种交替模式在语言模型工具调用中的典型实现：

~~~text
输入目标与已有观察
    ↓
提出当前行动（例如检索某文件）
    ↓
执行器检查权限、参数和预算
    ↓
工具真实执行并返回Observation
    ↓
根据新观察决定下一行动或结束
~~~

ReAct强调基于真实观察继续推进行动，而不是一次性臆造全部工具结果。论文提出推理与行动交织的思想，不意味着部署时应当向最终用户展示所有内部推理文本，也不意味着模型的推理文本能够代替权限检查。

在代码审计中，第一次读取auth.py可能发现调用发生在另一文件。下一步检索目标随观察而变化；如果提前生成一百条固定搜索路径，可能浪费大量工具预算。

### Plan-and-Execute为什么适合可拆分任务

如果任务需要先修复再测试，有些依赖在执行前就已经明确。此时可先产生子任务计划：

$P=(a_1,a_2,\ldots,a_n).$

执行器逐步检验每步的前置条件。若某步结果与预测不同，规划器修改剩余计划，而不是继续执行过期动作。

~~~text
Planner → 子任务队列 → Executor → Verifier
                 ↑                   │
                 └── 更新状态/重规划 ─┘
~~~

ReAct偏向一次产生一步行动，Plan-and-Execute更强调跨多步的任务结构，但二者不互斥：上层使用任务DAG，下层各子任务仍然可以通过观察—行动循环执行。

### 图状态机适合哪里

如果流程中有确定的分支和审批：

~~~text
接收任务 → 读取代码 → 产生补丁 → 人工审查
                               ↙       ↘
                             通过      拒绝
                              ↓         ↓
                           回归测试   终止/修改计划
~~~

可以把节点映射为输入输出契约明确的函数，把边映射为状态转换条件。LangGraph等框架提供图状态、检查点和中断恢复，但它们不会让未经授权的工具自动变安全。

### 三种结构怎样选择

| 任务特点 | 倾向的编排 | 主要风险 |
|---|---|---|
| 下一步取决于当前检索结果 | ReAct式观察—行动循环 | 无边界循环与模型误判 |
| 已知多个阶段的强依赖 | Plan-and-Execute / DAG | 计划过期和错误依赖 |
| 审批、恢复与分支较多 | 图状态机 | 节点重执行和状态版本 |
| 子任务复杂且需要审批 | DAG + 子任务ReAct + 持久状态图 | 跨层状态和权限不一致 |

框架名称不是性能证明。应该比较任务成功率、调用次数、权限、预算和真实恢复效果。

### 三种架构共享的执行接口

~~~python
from dataclasses import dataclass

@dataclass(frozen=True)
class Action:
    name: str
    arguments: dict
    expected_version: int

@dataclass(frozen=True)
class Observation:
    ok: bool
    next_state_version: int
    evidence_id: str | None
~~~

规划器提出Action，执行器通过独立授权和输入校验后才返回真实Observation。模型可以生成候选动作，但不能根据自己输出的文字修改权威任务状态。

## 从规划器到完整项目：亲手实现一个可验证的代码修复Agent

### 一次代码修复不只是生成新函数

假设项目里的计算函数应执行两数相加，却错误地使用减法：

~~~python
def add(a, b):
    return a - b
~~~

模型提出正确候选代码并不复杂。但一个具有实际写入能力的Agent，还需要回答：

- 修改目标文件是否在当前任务允许的路径中？
- 它看到的文件版本是否仍是当前版本？
- 是否有人批准把修改写入工作区？
- 候选代码是否通过独立于生成器的验收测试？
- 执行过程中出错，是否保留了原文件？
- 操作确认消息丢失后，重新提交会不会造成第二次写入？

因此，本节将Agent拆成六种职责明确的组件，真正运行一次观察、提议、审核、验证与提交的闭环。

### 第一步：定义可验证任务

设任务为：

$
\mathcal T=(F,\ H_0,\ \mathcal A,\ G,\ B).
$

其中 $F$ 是获授权目标文件；$H_0$ 是观察时文件内容的SHA-256指纹；$\mathcal A$ 是允许执行的操作集合；$G$ 是必须通过的验收条件；$B$ 是预算。

在本实验中：

- 只能修改临时目录中的calculator.py；
- 初始文件包含带缺陷的add(a,b)函数；
- 候选只能替换这个已知函数；
- 需要显式批准才能把修改提交到工作区；
- 必须通过整数、负数和零值的测试；
- 同一操作ID只能具有一种固定修改内容。

这与生产环境的“用户自然语言要求修复整个项目”差距很大，但能在不依赖网络API的情况下逐步验证完整执行协议。

### 第二步：将观察结果绑定版本

Agent观察文件后，得到原始文本 $x$ 和指纹：

$
h_0=\operatorname{SHA256}(x).
$

候选补丁作为结构化对象保存：

~~~python
from dataclasses import dataclass

@dataclass(frozen=True)
class Proposal:
    relative_path: str
    original_sha: str
    replacement: str
    operation_key: str
~~~

如果文件被其他程序更改，即使修改仍然看起来正确，旧补丁也不能直接覆盖新内容。提交前读取当前文件并检验：

$
h_{\rm current}=h_0.
$

若不相等，返回“版本冲突”，重新观察并生成适用于新版本的补丁。这个策略类似乐观并发控制。

### 第三步：区分计划许可与执行许可

规划器能够产生候选修改，但系统不应让它自行决定是否越过人工审批。审批门槛由工具执行器检查：

~~~python
if not human_approved:
    raise PermissionError("write requires approval")
~~~

此外，还要检查文件必须属于明确授权的集合、路径不能逃逸工作区，以及调用不能超出预算。文件名只是参数，不是资源访问权限。

截至2026年的OpenAI Agents SDK官方文档将输入Guardrails、输出Guardrails、工具Guardrails与人工审批分成不同环节，并指出Agent级输入/输出Guardrail并不自动覆盖每个中间工具调用。

因此对修改文件或提交工单等动作，应在**真正产生副作用的工具边界**实施检查，不能只在第一次收到用户请求时检查一次。

### 第四步：在提交前运行独立验收

候选代码通过语法分析不代表业务正确。Python里减法函数也可以合法解析，甚至在某些输入上产生偶然正确的结果。独立验收至少包括：

1. 代码符合本任务允许的结构；
2. 已知错误能够被正确修复；
3. 不同输入类别的回归样例全部通过；
4. 修改范围与预期一致。

本例采用AST白名单，只允许单个没有装饰器、没有额外调用的add(a,b)函数，其主体只能是a+b或a-b，且没有其他语句。之后才运行一组明确的算术测试。

这种严格白名单仅适合极小的教学对象，**不是安全执行任意第三方Python代码的沙箱**。实际代码审计Agent应使用隔离进程、最小文件和网络权限、独立镜像及资源限制，不能因为AST检查通过就随意执行未知项目。

### 第五步：暂存、验证和原子替换

将修复内容先写入同一工作目录的暂存文件，独立测试通过且目标指纹仍匹配后，再进行原子替换：

~~~text
已授权的目标文件
       ↓ 观察 + SHA-256
生成固定范围的候选修复
       ↓ 审批检查
暂存候选文件
       ↓ AST范围检查 + 独立测试
再次确认原文件SHA-256
       ↓ 同文件系统原子替换
写入操作结果与证据
~~~

这里所说原子替换只表示使用同一文件系统上的替换机制尽量避免半成品目标文件，并不意味着提供数据库与文件联合事务，也不保证突然断电后的持久性。在多进程真实系统里，还需要持久锁或原子版本协议处理提交竞争。

### 第六步：让重试与副作用彼此可区分

设某次提交的业务操作键为 $k$，将路径、旧指纹和新内容组成载荷指纹 $d$。

记住：

$
(k,d)\mapsto r,
$

其中 $r$ 是已确认的结果。若再次收到相同的 $(k,d)$，直接返回原结果；若相同 $k$ 携带不同 $d$，拒绝冲突。

在教学代码中，这个映射保存在进程内存，因此只能验证**同一进程的重复调用**。真实长任务恢复需要把结果记录持久化，并确认异常重启后仍能恢复状态。

这个细节十分关键：不能因为一份演示使用了操作键，就声称它在多机、断电、网络故障条件下拥有业务效果恰好一次的保证。

### 用状态不变量证明修复流程的正确性

可以定义以下三个不变量：

$
\operatorname{Committed}\Rightarrow
\operatorname{Approved}\land\operatorname{TestsPassed},
$

$
\operatorname{Committed}\Rightarrow
\operatorname{SHA256}(\text{原文件})=h_0
\quad\text{（提交前检查时刻）},
$

$
\operatorname{ReplaySameKeySamePayload}
\Rightarrow
\Delta\operatorname{SideEffects}=0.
$

第一个性质保证没有通过审批与独立测试的修改不能进入工作区；第二个性质在单进程模型中防止错误覆盖旧版本；第三个性质要求相同操作的重放不增加本地副作用计数。

生产版本还应验证文件锁与竞争窗口、原子提交结果持久化、工件签名和身份授权有效期。

### 运行完整项目

~~~bash
python examples/verified_code_repair_agent.py
~~~

程序使用Python标准库自动建立临时工作区，并在执行后清理。无需Docker、模型API或真实GitHub凭证。

实验会依次执行：

1. 证明原有减法函数无法通过目标算术测试；
2. 生成有限范围的加法修复候选；
3. 拒绝未获批准的写入请求；
4. 拒绝语法合法但业务测试失败的候选；
5. 批准修复并通过独立测试，原子替换文件；
6. 再提交同一操作键，副作用计数仍为1；
7. 拒绝旧版本指纹、越权路径与包含额外代码的候选。

### 如何升级为真正的代码Agent

当教学例子运行通过后，可以沿以下方向增加复杂度，但每项都需要配套验收：

- 将确定性候选生成器替换为实际LLM接口；结构化输出仍须被当作待验证数据；
- 将单个文件扩展为多文件修改，绑定一个不可变Git提交快照；
- 将固定算术测试扩展为独立测试框架，记录测试版本、退出码与真实日志；
- 使用受限进程或沙箱执行未知项目代码，并明确网络、文件和资源授权范围；
- 将内存操作日志改为持久数据库，模拟进程退出后的恢复；
- 为并发Agent加入共享黑板版本检查和冲突重新规划；
- 引入固定难度的代码任务集，分别测量成功率、成本、延迟及错误修改率。

多Agent不应成为第一步。先让一个Agent能够稳定、可验证、可恢复地完成一条任务，再决定哪些环节值得并行。

### 练习与解答

**题一：** 代码能通过Python语法检查，为什么仍不能直接提交？

**解：** 语法正确只说明代码结构可以被解析，不说明实现满足任务条件。原始减法缺陷也能通过语法检查，必须使用独立业务测试。

**题二：** 观察时文件SHA与提交前不一致，为什么不应继续写入？

**解：** 目标已经变化，旧补丁的前提可能失效。直接写入可能覆盖其他执行者的修复，必须重新获取状态再计算。

**题三：** 同一进程的重复调用没有造成二次写入，能否说明系统已经实现崩溃后的恰好一次？

**解：** 不能。内存记录在进程退出后可能丢失，而且还没有覆盖外部系统提交成功但本地确认丢失的情况，需要持久日志与远端幂等或查询协议。

**题四：** 测试Agent自己写入“PASS”文字是否满足独立验收？

**解：** 不满足。实际执行器应运行有明确版本、输入和断言的测试，并保留可信退出状态与结果证据；模型生成的PASS只是未经验证的文本。

### 为什么模拟失败的语义必须准确

实验中，模拟失败被定义为：动作确定没有改变状态。因而可以删除对应可用边并重新搜索。真实网络请求超时时，外部动作可能已经发生，必须先查询执行状态。不能把实验中的“失败无副作用”假设直接用于付款、数据库修改或删除文件。

## 习题与解答

### 练习：BFS与A*可能得到不同路线

图中“开始→初查”成本1，“初查→目标”成本10，“初查→审核”成本1，“审核→目标”成本2。

**解：** BFS按照边数会优先考虑两步路线“开始→初查→目标”，成本11；最小成本路线是“开始→初查→审核→目标”，成本4。BFS的最少边数保证不适用于成本不等的图。

### 练习：启发式可采纳性

一个状态的真实最优剩余成本为7。若启发式分别估计5和9，哪一个可采纳？

**解：** 估计5不高于7，满足可采纳要求；估计9超过真实值，不可采纳。估计5仍需检查图中所有相关边是否满足一致性条件，不能由单点估计直接推出。

### 练习：随机成本

快速路径即时成本1，80%直接成功，20%需要再花10。求期望成本。

**解：** 由全期望公式 $1+0.8\times0+0.2\times10=3$。

### 练习：告警后验

先验故障概率0.1，真实故障告警概率0.8，正常误报概率0.05。

**解：** 告警总概率 $0.8(0.1)+0.05(0.9)=0.125$，故障后验为 $0.08/0.125=0.64$。
